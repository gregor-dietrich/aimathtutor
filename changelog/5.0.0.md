# AIMathTutor Changelog — Version 5.0.0

## Added

- Database schema is created and upgraded automatically on startup.
- Four designs (Vellum, Power-Up, Vibranium and Chalkboard) and a colour mode
  (Light, Dark or Follow system), chosen per user under Settings → Appearance
  and saved to the account. Existing and new accounts start with Vellum
  following the system setting. The fonts of the designs are served by the
  application itself.

## Changed

- Quarkus platform version updated from 3.40.1 to 3.40.1.1
- Vaadin version updated from 25.3.1 to 25.3.3
- New installations no longer contain demo lessons, exercises, sessions or
  teacher/student accounts.
- New installations no longer contain an `admin` account with the password
  `admin`. The first admin account is created on the first start from the
  `APP_BOOTSTRAP_ADMIN_USERNAME` (default `admin`) and
  `APP_BOOTSTRAP_ADMIN_PASSWORD` settings; without a password, the application
  refuses to start.
- Success, warning and error colours are easier to read, especially in dark
  mode.
- Warning messages are now shown in yellow.
- The "Reset Filters", "Enter Custom Problem" and "Show Published Only" buttons
  use the default button style.
- Badges have a new, rounder look.
- The colour-mode button in the top bar now saves the choice to the account, and
  is hidden when signed out.
- The dashboard chart "Top Categories by Completion" is now "Top Exercises by
  Completion", which is what it counts.
- The user ranks list shows an icon only for each permission a rank holds; a
  rank without the Admin View permission no longer shows a ban icon.

## Fixed

- The user and rank administration no longer offers what the signed-in
  administrator is not allowed to do: users and ranks above their own rank
  cannot be opened, edited or deleted, the rank list for a user leaves out
  higher ranks, and permissions they do not hold cannot be ticked on a rank.
- The ranks list and the rank choice for a user show every rank, not only the
  newest 100.

- Usernames may contain only the letters a–z, digits, dots, underscores and
  hyphens, so two accounts can no longer look identical through spaces,
  invisible characters or lookalike letters. Spaces around a name are refused
  instead of removed.
- Only administrators who may view the administration can activate or ban
  accounts, also when creating one, and only those who may edit ranks can change
  an existing account's rank. For anyone else, a new account is created inactive
  and not banned, an existing account keeps its status and rank, and the rank
  field is read-only when editing an account.
- Saving a user or rank in the administration no longer silently undoes a
  change another administrator made in the meantime, such as a ban or a removed
  permission. The save is refused with a request to refresh the list and edit
  again. A user changing their own appearance or avatars does not count as such
  a change.

- Password changes show the specific rejection reason and allow correcting the
  input, including the documented 72-character maximum.
- AI providers fail promptly on permanent HTTP client errors, such as an invalid
  API key, instead of retrying the same rejected request. The tutor then gives
  no feedback instead of generic fallback hints, and the chat says that it is
  not available.
- Permission checks and rank display no longer load every member of the rank.
- Production startup reports recovery instructions while no active administrator
  exists, for example after deactivating former demo accounts removed the last
  one.
- Production deployment uses the tracked `deploy/compose.yml`, with matching
  PostgreSQL pins and complete optional Ollama instructions.
- OpenAI Organization ID instructions point to Admin Settings, where the value is
  stored and used.
- In dark mode, the page background below the content and the math workspace
  (canvas, on-screen keyboard and help) are now dark too.
- "Follow system" now follows a change of the operating system's setting while a
  page is open. The math workspace switches from dark to light only on the
  next page load.
- The colour mode no longer carries over to the next sign-in in the same
  browser.
- The comments button in the exercise administration is labelled "Show
  Comments", which is what it does.
- The comment form on an exercise sits on one card, with space between the text
  box and the "Post Comment" button.
- Exercise hints are split only at line breaks, as the editor describes, so a
  hint may contain a semicolon or a vertical bar. Hints that were separated by
  one of those on a single line now show as one hint; put each on its own line.
  The former demo exercises of an upgraded installation show their hints one by
  one instead of as a single bracketed list, unless they were edited.
- Repeated failed sign-ins now lock out for longer each time, up to one hour.
  Failures are remembered until an hour after the lockout ends; before, the
  count started over after a minute, so guessing could continue at several
  attempts a minute. A successful sign-in forgives only the failures of the
  account that signed in, so signing in between guesses at other accounts no
  longer resets the limit for that address. When several people share one
  address, such as a school network, each further account that signs in from it
  within an hour forgives one more failed sign-in, so occasional typos do not
  lock everyone out.
- The sign-in limits treat all IPv6 addresses of one network (the same /64
  prefix) as one address, so switching between them no longer avoids a
  lockout.
- Behind a reverse proxy, the sign-in limits use the client address the proxy
  adds to `X-Forwarded-For` instead of the first entry, which the client can set
  itself. An entry that is not an IP address is no longer used; the proxy's own
  address counts instead.
- Failed sign-ins with many different usernames no longer lift an existing
  lockout.
- A production start no longer replaces a missing encryption key file with a new
  key while the database holds encrypted email addresses. It refuses to start
  and names the missing key file, so the key can be restored and the stored
  addresses stay readable. A first start on an empty database still creates the
  key.
- A page left open after its session ended (a password change, or the account
  being banned, deactivated or deleted) no longer edits, deletes or reports
  comments, changes avatars, records exercise progress, asks the AI tutor or
  lists users; it returns to the sign-in page instead. An open user list or
  group member dialog also stops loading once the account loses access to the
  administration, as do the open administration pages for sessions, progress,
  comments, groups and exercises, and the dashboard. Saving or deleting users,
  ranks, groups, lessons or exercises in the administration after the session
  ended, changing a group's members, or saving, resetting or testing the
  connection of the AI settings, also returns to the sign-in page instead of
  showing an error.
- Changing a group's members without permission to edit groups, or adding a
  user who is already in the group, says so instead of reporting an
  unexpected error. So does saving, resetting or testing the connection of the
  AI settings without permission to edit them.
- Saving an invalid AI setting, such as an out-of-range temperature or a
  provider address that is not allowed, shows what is wrong with it instead
  of a generic error.
- An unexpected failure of a connection test on the AI settings page shows a
  plain message instead of internal error details, and the page's buttons stay
  disabled until the test completes.
- A connection test without a Google or OpenAI API key set reports that the
  key is not configured instead of reporting the endpoint as reachable, and
  the AI tutor no longer sends the placeholder as a key.
- An exercise whose progress tracking cannot start shows an error instead of
  opening without recording progress.
- The dashboard's average success rate leaves out accounts without any recorded
  actions, which it counted as 0%.
- The dashboard no longer loads every recorded session to show its figures.
- The first day of the dashboard's daily sessions chart counts the whole day,
  not only the sessions after the current time of day.
- A change to the AI settings now always takes effect. A setting read at the
  moment it was saved could keep its old value until the next restart or the
  next save of that setting.
- Google and OpenAI addresses are now also refused when their host name points
  into other address ranges reserved for private or special use, such as
  carrier-grade NAT and benchmarking networks.
- The AI provider connection test no longer shows the low-level network error
  when an endpoint cannot be reached; the server log has the details.
- "Reset to Defaults" on the AI settings page no longer fails where the Google
  or OpenAI API hosts cannot be resolved, for example on an Ollama-only install
  without internet access, or where the operator narrowed the allowed Google or
  OpenAI hosts. On such an install the restored default Google or OpenAI
  address is still refused when it is used.
- The AI settings page no longer stops responding while a slow database loads
  its settings.

## Upgrade Notes

- A Google or OpenAI host added to `app.security.allowed-google-hosts` or
  `app.security.allowed-openai-hosts` is now refused if its name points into
  carrier-grade NAT (such as a Tailscale address), benchmarking, documentation
  or another range reserved for special use, both when the setting is saved and
  on every request. Ollama hosts are not affected.
- An existing account whose username contains any other character, such as a
  space, an accented letter or `@`, still signs in, but the user dialog refuses
  to save it until it is renamed. A password reset does not need the rename.
  `APP_BOOTSTRAP_ADMIN_USERNAME` is no longer trimmed: a first start on an empty
  database refuses a value with surrounding spaces.
- Upgrade to the latest 4.0.x first. Its database is adopted automatically
  without manual SQL. Databases from older releases must be brought to the 4.0.x
  schema before upgrading.
- The database no longer needs an initialization script. Remove the
  `docker-entrypoint-initdb.d` mount from existing Docker Compose files: if the
  database volume is ever recreated while it is still mounted, the old script
  creates the former demo accounts with their publicly known passwords.
- If the `admin` account still has the password `admin`, the application refuses
  to start until `APP_BOOTSTRAP_ADMIN_PASSWORD` is set, and then replaces that
  password once. Accounts with any other password are not affected. Remove the
  setting after the first successful start.
- The former demo accounts `teacher`, `student1` and `student2` are deactivated
  on startup while they still accept their publicly known passwords. Set new
  passwords before reactivating them.
- The repository's `docker-compose.yml` now builds the app image from the
  checkout and is for development. Deploy with `deploy/compose.yml`, which runs
  the published image: download it as described in the Quickstart, but into the
  directory of the existing deployment, beside its `.env`, replacing the old
  `docker-compose.yml`. Compose names the database and encryption key volumes
  after that directory, so a new directory starts with an empty database and a
  new key. If the old stack ran from a checkout, use a new directory and set
  `COMPOSE_PROJECT_NAME` in its `.env` to the checkout directory's name. Then
  run `docker compose pull` and `docker compose up -d --remove-orphans`: the
  pull replaces a cached `latest` image, and `--remove-orphans` stops services
  the new file no longer defines, such as a pgAdmin published on all
  interfaces.
- The images never read `JAVA_OPTS` or `JAVA_OPTS_APPEND`. Move such options to
  `JDK_JAVA_OPTIONS`.
- Behind a reverse proxy, list the address of every proxy in
  `app.security.trusted-proxy-ips`, not only the one the application connects
  from. Each listed proxy must append the address it received the request from
  as the last `X-Forwarded-For` entry, without a port; never list one that passes
  the header on unchanged, or clients can choose their own address. A proxy that
  is missing from the list or appends a port makes all sign-ins count against
  one proxy address. Failed sign-ins from anyone can then lock everyone out for
  up to an hour, and a failure right after the lockout ends renews it. Users who
  share one public address, such as a school network, share that lock the same
  way.
- Restarting the application clears all sign-in lockouts; it also ends every
  open session. A lockout of a whole address is logged as a warning naming that
  address (an IPv6 network by its /64 prefix); retention of and access to the
  logs are the operator's responsibility.
- Entries of `app.security.trusted-proxy-ips` must be IP addresses, IPv4 in full
  four-part form; hostnames and address ranges are ignored, with a warning in the
  log. Leave Quarkus's own `quarkus.http.proxy.proxy-address-forwarding` off:
  `app.security.trusted-proxy-ips` replaces it for sign-ins.
- Keep the encryption key file of the existing deployment (with Compose, its
  `aimathtutor_keys` volume): once the database holds email addresses, the
  application no longer starts without it. Without a backup, see "Lost
  encryption key" in the README.
